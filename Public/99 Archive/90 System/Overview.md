# Vault Overview

This is an overview of how the vault is structured and maintained: the folder layout, note types, schemas and CI, sync, and the skills that keep it tidy. The rules themselves live in [[CONVENTIONS]] and note schemas in `91 Tooling/schemas/`; this note explains them and how they fit together.

## Purpose and principles

- **Predictable over clever:** a fixed folder map, a small set of note types, consistent properties. Claude queries structure; it guesses at chaos.
- **One contract, three files:** `90 System/Claude/CONVENTIONS.md` holds the rules in prose; `91 Tooling/schemas/` holds the machine-checked schemas, `properties-schema.yaml` for YAML frontmatter and `structure-schema.yaml` for folder layout. Every skill reads all three first, and validation scripts enforce the schemas on Claude's runs and in CI. This overview is background, not part of the contract.
- **Link, don't duplicate:** each fact lives in exactly one note. Hobbies and Life Admin link to projects, knowledge and references rather than copying them.
- **Privacy by access, not by instruction:** Claude only ever gets the folder it is allowed to see.
- **Reversible:** every Claude edit is versioned in Git and logged.
- **Schemas before automation:** use real notes for a few weeks before building skills on top of them.

## Privacy boundary

Obsidian opens the whole vault; Claude is connected only to `Public/`, so `Private/` is unreachable at the OS level.

```
Vault/         ← Obsidian opens this (sees everything); lives in iCloud Drive, synced to GitHub
├── Public/    ← the only folder connected to Claude
└── Private/   ← never connected; encrypted on GitHub with git-crypt
```

- Never connect the vault root itself — that would expose `Private/`.
- Private notes may link to Public notes. **Public notes never link to Private notes**, and a GitHub Action checks this on every push (see [[#The GitHub Actions]]).
- Private holds: account numbers, salary and tax documents, health records, journal entries not for analysis. Passwords belong in a password manager.
- `Private/` syncs through iCloud and GitHub like the rest of the vault. On GitHub its contents are encrypted with git-crypt; file names, folder names and commit messages are not, so keep sensitive details out of them.
- Meld Encrypt is a plugin used to encrypt a whole note or parts of a note within Obsidian. It can be used for single notes that should also be encrypted on your Apple devices.
- `.obsidian/` (settings, plugins) sits at the vault root, outside Claude's reach. Plugin changes are done by hand.

## Folder structure

Inside `Public/`, a numbered PARA-style layout separates finite projects, ongoing hobbies, life admin, and knowledge. The first digit is the band, the second the position; subfolders are not numbered. As an example:

```
Public/
├── 00 Inbox/            quick captures; Claude triages
├── 01 Logs/             Daily/, Weekly/ (generated by skills), Monthly/
├── 10 Projects/         finite goals with an end date
├── 20 Hobbies/          one domain per hobby (skeleton below)
│   ├── Music/           Composers/, Piano/, Violin/ (instruments are subdomains)
│   ├── Fitness/
│   └── Travel/
├── 30 Life Admin/       one domain per responsibility (skeleton below)
│   ├── Finance/
│   ├── Health/
│   ├── Home/
│   ├── Planning/
│   └── Work/
├── 40 Knowledge/
│   ├── Sources/         Papers/, Books/, Courses/, Articles/
│   ├── Concepts/        atomic notes, one idea each (flat)
│   └── Maps/            one hub per field: CS, Math, Physics, Music Theory, Philosophy
├── 50 References/       look-up info and how-tos
├── 90 System/           Templates/, Bases/, Claude/ (CONVENTIONS.md, changelog), this overview
├── 91 Tooling/          schemas, validation scripts, tests
├── 98 Attachments/      images, PDFs and files embedded in notes
└── 99 Archive/          retired notes; mirrors the original path
```

**Placement rule:** has a finish line → Projects. A hobby you keep doing → Hobbies. A responsibility that never ends → Life Admin. Something learned → Knowledge. Something looked up → References. Nothing fits clearly → it stays in the Inbox. For notes Claude generates, it asks you.

Knowledge is organized by links, not folders: a concept like the Fourier transform sits once in `Concepts/` and is linked from the Math, Physics and Music Theory maps.

## Hobby and Life Admin skeleton

Every folder directly under `20 Hobbies/` or `30 Life Admin/` is a **domain**, and every domain has the same shape: one hub note plus up to three kinds of subfolder: Items, Logs, and Plans. A domain holds only what is about your own doing or owning; everything else lives once, elsewhere, and the hub links to it.

```
<Domain>/
├── <Domain>.md       hub (required): what this is, what's active, links out
├── <Plan>.md         standing plan notes (optional): Budget.md, Schedule.md
├── <Items>/          things you track or own, one note each (optional, any number)
├── <Logs>/           dated records of what you did (optional, any number)
├── <Plans>/          a series of standing plans, e.g. Weekly Routines/ (optional)
└── <Subdomain>/      a nested domain with the same shape (optional)
```

Subfolders and documents within a domain each have roles and are named for what they hold (e.g., `Pieces/`, not `Items/`); `structure-schema.yaml` records each folder's role and allowed note types.

| Role  | Holds                                              | Test                                   | Examples                                                  |
| ----- | -------------------------------------------------- | -------------------------------------- | --------------------------------------------------------- |
| Hub   | Overview, current focus, links out to other notes  | One per domain, named after the folder | Piano.md, Finance.md                                      |
| Items | One note per thing, with its own status or history | Do I track the state of this thing?    | Pieces/, Composers/, Exercises/, Trips/, Places/, Assets/ |
| Logs  | One note per date or period                        | Did this happen on a date?             | Practice/, Sessions/, Spending/                           |
| Plans | What you follow repeatedly until you change it     | Does it repeat with no end date?       | Routines/, Budget.md, Schedule.md                         |

**Hub body.** Every hub uses the same headings, and most of it is queries, so nothing is copied:

```markdown
# Piano
One paragraph: what this is to you and current goals.

## Now        Bases view: items with an active status; Tasks query for this folder
## Projects   Bases view: projects where area = [[Piano]]
## Plans      links to the current plan notes
## Recent     Bases view: the latest log notes
## Links      the relevant Maps in 40 Knowledge and notes in 50 References
```

**What stays out of a domain:**

| If it is…                                                                     | It goes in...                          | Within the domain...                               |
| ----------------------------------------------------------------------------- | -------------------------------------- | -------------------------------------------------- |
| A goal with an end (a June recital program, a kitchen repaint)                | 10 Projects/, with `area: "[[Piano]]"` | It appears in the hub's Projects view on its own   |
| Something learned (harmony, training science, how index funds work)           | 40 Knowledge                           | A link to the Knowledge Map under Links            |
| A how-to or look-up (scale fingerings, form cues, tax deadlines, policy text) | 50 References                          | A link from the hub or from the item that needs it |

**Domain Examples:**

| Domain                    | Items                      | Logs             | Plans                  |
| ------------------------- | -------------------------- | ---------------- | ---------------------- |
| Music                     | Composers/                 |                  |                        |
| Music/Piano, Music/Violin | Pieces/, Technique/        | Practice/        | Practice rotation      |
| Fitness                   | Exercises/                 | Sessions/        | Routines/              |
| Travel                    | Trips/, Places/            |                  |                        |
| Finance                   | Accounts/ (no numbers)     | Spending/        | Budget.md, Wishlist.md |
| Health                    |                            | Health Log/      | Eating plan            |
| Home                      | Assets/, Contractors/      | Maintenance Log/ |                        |
| Planning                  |                            |                  | Schedule.md, To-dos.md |
| Work                      | Benefits/ (your elections) |                  |                        |

Placement decisions that follow from the skeleton:

- **Technique/** holds only drills you track (a scale and its current tempo). Technique explanations live in 40 Knowledge/ or 50 References/.
- **Exercises/** holds your working weights and notes per exercise. Form how-tos live in 50 References/.
- **Nutrition** guidance lives in 50 References/; your own eating plan is a Health plan note.
- **Travel ideas** are trip notes with `status: idea`; there is no Ideas/ folder.
- **Trips are items** even though they end: one trip note is both the plan and the record, so no project duplicates it.
- **`reference` is only for 50 References.** Notes about your own situation (accounts, contractors, benefit elections) are items in their domain.
- **Composers are items** shared by every instrument in Music/; biography and style analysis go to 40 Knowledge/.
- **Plan notes** (Budget.md, Schedule.md, Wishlist.md, To-dos.md, a practice rotation) have the `plan` type and sit at a domain root.

## Note types and properties

Every note outside `00 Inbox/` and `98 Attachments/` has a `type` from `properties-schema.yaml` and that type's properties. Every type requires `type`, `created` and `updated`, and may have `aliases`, `tags`, `claude` and `origin` (where the note came from). Folders and filename patterns belong to `structure-schema.yaml`; the "Lives in" column summarizes it.

| Note Type         | Lives in                                        | Required                      | Optional                                                                 |
| ----------------- | ----------------------------------------------- | ----------------------------- | ------------------------------------------------------------------------ |
| daily             | 01 Logs/Daily                                   | date                          | energy (1–5), sleep_hours, highlights                                    |
| weekly            | 01 Logs/Weekly                                  | week, start                   | practice_minutes, workouts, spending_total (computed, never typed)       |
| monthly           | 01 Logs/Monthly                                 | month                         |                                                                          |

Schema rules that shape every note:

- **One property name, one value type, vault-wide.** `difficulty` is always a number; a text grade gets its own name, `grade`.
- **No nested objects.** Structured data goes in a body table: spending categories, workout sets.
- **Fixed vocabularies.** Statuses, fields, focus areas, eras, muscle groups, equipment and categories come from lists in the schema. New values, properties or types are proposed, approved, added to `properties-schema.yaml`, then used.
- **Four tags only:** `#inbox`, `#review`, `#idea`, `#question`. Everything else is a property.

## Schemas, validation and CI

Every rule a machine can check lives in a schema in `91 Tooling/`, and scripts enforce them in two places: Claude runs them after each skill run, and GitHub Actions run them on every push. [[CONVENTIONS]] keeps only the rules that need judgment, and points to the schemas instead of restating them.

```
91 Tooling/
├── README.md                    type: system — what each file does, how to run it
├── schemas/
│   ├── properties-schema.yaml
│   └── structure-schema.yaml
├── scripts/
│   ├── vault.py                 shared loader: walks Public/, parses frontmatter, resolves types
│   ├── validate_properties.py
│   ├── validate_structure.py
│   ├── check_private_links.py   CI only: no link in Public/ may resolve into Private/
│   └── validate.py              runs every check; exit code for CI, --json for Claude
├── tests/fixtures/              small sample vaults that must pass or fail
└── requirements.txt             pinned PyYAML
```

### The schemas

| Schema | Stage | What it checks |
| --- | --- | --- |
| `properties-schema.yaml` | Core | Frontmatter: each property's one value type, vocabularies, required and optional properties per note type, value constraints |
| `structure-schema.yaml` | Core | Layout: the allowed top-level folders, every domain and its role folders, which note types live in each folder, filename patterns, hubs present, flat folders, allowed non-note files |
| `body-schema.yaml` | Planned | Required headings and tables per type: hub headings, concept Connections and Sources, the spending Categories table, the session sets table, daily and weekly sections. Templates can be generated from it |
| Typed links | Planned, inside the properties schema | `link: composer` instead of `link: true`: `piece.composer` must point to a composer, `project.area` to a hub, `session.exercises` to exercises |
| `access-schema.yaml` | Planned | Per folder, what Claude may do: create, edit, regenerate whole (daily and weekly notes) or read only. CI can then check that Claude's commits touched only allowed files |
| Template check | Planned, a script rather than a schema | Each template in `90 System/Templates/` yields a note that passes every schema |

- **One home per rule:** the core schemas join on note type names. A type's folders and filename pattern are declared once, in the structure schema; its properties once, in the properties schema.
- **Approval enforces itself:** an undeclared folder fails validation, so a new hobby or area means a schema edit, which needs your approval.
- **Shared version:** CONVENTIONS.md and both schemas carry one version number and change together.

### Where validation runs

| Where | When | On failure |
| --- | --- | --- |
| Claude | End of every skill run (`validate.py --json`) | Fixes what it broke; reports the rest in the changelog |
| GitHub Actions | Every push to main, plus a weekly scheduled run | Red check and a JSON report; vault-health reads the latest result |
| Any desktop | On demand (`python "91 Tooling/scripts/validate.py"`) | Prints the failures |

The private-link check runs only in GitHub Actions: Claude can't see `Private/`, so it can't tell whether a link points there.

### The GitHub Actions

Two workflows live in `.github/workflows/` at the repository root.

**`validate.yml`** — schemas:

1. Check out the repository. CI gets no git-crypt key, so the contents of `Private/` stay encrypted and are never read.
2. Set up Python and install `requirements.txt`.
3. Run the test fixtures, so a broken schema or script fails before the vault is judged.
4. Run `validate.py` over `Public/` and upload the JSON report as a build artifact.
5. On failure, mark the commit red, and optionally open or update a single "Vault validation" issue.

**`private-links.yml`** — no links from Public into Private:

1. Check out the repository, again without the git-crypt key. git-crypt encrypts file contents, not file names, so the list of files in `Private/` is still visible.
2. Collect every link in every note in `Public/`: wikilinks (`[[Note]]`, `[[Note|text]]`, `[[Note#Heading]]`), embeds (`![[file]]`) and Markdown links to local files.
3. Resolve each link the way Obsidian does: an exact path if one is given, otherwise the file with that name anywhere in the vault.
4. Fail if any link resolves to a file under `Private/`, or if a name is ambiguous between a Public and a Private file. Print each offending note and link.

Both workflows share these properties:

- **CI reports; it doesn't block.** Phone edits reach GitHub through the Mac's auto-commit, so there is nothing to reject. For the same reason there is no pre-commit hook: it would stop Obsidian Git's auto-commits.
- **Out of Claude's reach:** the workflows live outside `Public/`, so Claude can neither see nor change them.
- **Deployment, later:** there is nothing to deploy yet. A later workflow could regenerate templates from the body schema and commit them.

## Everyday lists

Three living lists — a schedule, a wishlist and small to-dos — are plan notes: you keep following them, and they never finish.

| Note | Path | Format | How skills use it |
| --- | --- | --- | --- |
| Daily and weekly schedule | `30 Life Admin/Planning/Schedule.md` | A weekday table, or recurring tasks (`- [ ] Practice piano 🔁 every day`) if you want to tick habits off | daily-note copies today's items into the daily note; weekly-review compares the plan with what happened |
| Wishlist | `30 Life Admin/Finance/Wishlist.md` | Table: Item, Category, Est. price (USD), Priority, Link. Category uses the `spending_category` vocabulary | spending-import can flag a wishlist item when it shows up in a statement |
| Small to-dos | `30 Life Admin/Planning/To-dos.md` | Tasks syntax, due date optional: `- [ ] Return library book 📅 2026-10-30` | daily-note lists open and due items with a Tasks query |

- **Planning domain:** band folders hold only domains, so Schedule and To-dos live in `30 Life Admin/Planning/`, with hub `Planning.md`.
- **Type:** all three use the `plan` type.
- **Naming:** it is Schedule, not Routine. `routine` is the weekly fitness plan; Schedule.md links to the current fitness routine rather than repeating it.
- **Not on the wishlist:** pieces you want to learn stay as `piece` notes with `status: wishlist`. Wishlist.md is for things to buy.
- **To-dos with a home:** a task tied to a domain or project (fix the faucet → Home) can live in that note instead; the Tasks query finds it anywhere. To-dos.md is the catch-all, and Claude never ticks a task off for you.

## Sync and backup

iCloud syncs the Apple devices, Git syncs the desktops, and the Mac connects the two. Obsidian Git works poorly on mobile, so phones and tablets rely on iCloud alone.

```
iPhone / iPad ── iCloud ──▶ Mac ◀── Git remote ──▶ Windows / Linux desktops
```

| Device | Syncs through | Obsidian Git |
| --- | --- | --- |
| iPhone, iPad | iCloud | Off |
| Mac | iCloud and Git | On: auto-commit, pull and push on an interval |
| Windows, Linux desktops | Git | On |

- **Vault location:** the vault lives in iCloud Drive's Obsidian folder so Obsidian on iOS can open it. On the Mac, set that folder to "Keep Downloaded" so iCloud never offloads files Git or Claude need.
- **The Mac is the bridge:** phone edits reach the other desktops only after the Mac commits and pushes them. Keep Obsidian Git's auto-commit and auto-pull on there.
- **Keep `.git` out of iCloud:** iCloud can corrupt Git's many small object files and would copy them to the phone. Either keep the Git directory outside the vault (`git init --separate-git-dir`) or rename it `.git.nosync` (iCloud skips `.nosync`) and point a `.git` file at it.
- **`.gitignore`:** `.obsidian/workspace*.json`, `.trash/`, `.DS_Store`. These change constantly and cause needless conflicts.
- **Remote:** a private GitHub repository holding the whole vault, `Private/` included.
- **git-crypt:** `.gitattributes` marks `Private/**` for encryption. Every desktop needs git-crypt installed and the repository unlocked; a locked clone shows `Private/` as unreadable binary files. Keep the key in your password manager, never in the vault.
- **Conflicts:** avoid editing the same note on the phone and a non-Apple desktop between Mac syncs. Git flags conflicts; iCloud quietly makes duplicate copies (`Note 2.md`), which vault-health reports.
- **Backup:** Git history is the real backup. iCloud is sync, not backup: a deletion syncs everywhere.

## Guardrails for self-maintenance

One hard boundary, several soft ones, and a full audit trail.

- **Hard:** folder access. Claude is connected to `Public/` only.
- **Schema-valid writes:** Claude runs `validate.py` before finishing, and every note it touched must pass both schemas. Claude never invents properties, types, vocabulary values, tags, folders or domains, and never edits CONVENTIONS.md or a schema without approval of the specific change.
- **No links into Private:** Public notes never link to Private ones; CI checks every push.
- **Read-only notes:** a `claude: read-only` property means read but never edit.
- **Generated notes:** daily and weekly notes are written entirely by skills, so Claude may create and rewrite them whole. Anything you write by hand goes in another note and gets linked.
- **No deletes:** Claude moves notes to `99 Archive/` instead.
- **Ask, don't guess:** ambiguous captures stay in the Inbox with a question.
- **Audit trail:** each skill run appends one line to `90 System/Claude/changelog.md`; Git holds the diffs.

## Rollout

Five phases; the schema test in phase 2 matters most, because schemas change once real notes hit them.

1. **Skeleton:** create the vault in iCloud Drive with the Public/Private split and the domain folders; finalize CONVENTIONS.md and both schemas; write the validation scripts, their tests and both GitHub Actions; write templates for daily, piece, concept, paper, trip. Set up Git: private remote, git-crypt for `Private/`, `.gitignore`, Git directory out of iCloud, Obsidian Git on every desktop.
2. **Real content:** migrate repertoire, current routine, a few papers and a past trip. Adjust schemas.
3. **First skills:** daily-note and inbox-triage; use them for two weeks.
4. **Core skills:** recall, weekly-review, ingest-source.
5. **Automation:** hobby planners, spending-import, quiz-me, vault-health on a schedule.
